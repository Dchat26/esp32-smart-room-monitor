## 1. `'BTN_PIN' was not declared in this scope` 컴파일 에러

**문제**
- 컴파일 시 `'BTN_PIN' was not declared in this scope`, `'digitalwrite' was not declared in this scope` 에러 발생

**원인**
- 문장 끝 세미콜론(`;`) 누락
- 함수 이름 대소문자 오류 (`digitalwrite` → 올바른 이름은 `digitalWrite`)
- C++은 대소문자를 구분하며, 세미콜론 하나가 빠지면 뒤쪽에서 엉뚱한 에러가 연쇄적으로 발생할 수 있다

**해결**
- 세미콜론 추가, 함수 이름 철자 수정
- 코드를 고친 뒤에도 에러 표시가 남아 있었는데, Wokwi는 **다시 실행(컴파일)해야 에러 표시가 갱신**됨

**배운 점**
- 에러가 여러 개면 **첫 번째 에러부터** 고친다
- `was not declared in this scope` → 철자 오류나 선언 누락을 먼저 의심한다

## 2. 버튼을 누르지 않아도 LED가 켜져 있음

**문제**
- 실습 A에서 버튼을 누르지 않았는데도 LED가 계속 켜져 있음

**원인**
- 푸시버튼 다리 4개 중 **같은 번호의 핀(2.l, 2.r)**에 GPIO19와 GND를 연결함
- 같은 번호 핀은 **버튼 내부에서 항상 연결**되어 있어, GPIO19가 늘 GND에 붙어 있는 상태
- 항상 `LOW` → `pressed`가 항상 `true` → LED 계속 켜짐

```
  1.l ──── 1.r    ← 내부에서 항상 연결
     [버튼]          (누르면 위아래가 이어짐)
  2.l ──── 2.r    ← 내부에서 항상 연결
```

**해결**
- GPIO19는 **2.l**, GND는 **1.r**처럼 **서로 다른 번호의 핀**에 연결
- 누를 때만 1번과 2번이 이어져 정상 동작

**배운 점**
- 부품의 내부 연결 구조를 먼저 확인해야 한다 (Wokwi에서는 핀에 마우스를 올리면 이름 확인 가능)
- 코드가 맞는데 동작이 이상하면 **배선을 먼저 의심**한다

## 3. 한 번 눌렀는데 여러 번 인식됨 (바운싱)

**문제**
- 실습 B(토글)에서 버튼을 한 번 눌렀는데 시리얼에 `press #`가 2~3개씩 찍힘
- 토글이 짝수 번 일어나 LED가 반응하지 않는 것처럼 보임

**원인**
- 기계식 버튼은 눌리는 순간 금속 접점이 수 ms 동안 **붙었다 떨어졌다를 반복**한다 (바운싱)
- ESP32는 매우 빠르게 `loop()`를 반복하므로 이 흔들림을 여러 번의 누름으로 인식

**해결**
- `millis()` 기반 디바운싱 적용: 값이 바뀔 때마다 시각을 기록하고, **50ms 동안 값이 유지될 때만** 진짜 입력으로 인정

```cpp
if (reading != lastReading) {
  lastChangeTime = millis();          // 흔들리면 타이머 리셋
}
if (millis() - lastChangeTime > DEBOUNCE_MS && reading != stableState) {
  stableState = reading;              // 안정된 변화만 확정
  if (stableState == LOW) { /* 토글 */ }
}
lastReading = reading;
```

- 결과: 한 번 누를 때마다 `press #`가 정확히 1씩 증가

**배운 점**
- 하드웨어 입력은 이상적인 0/1이 아니라 노이즈와 흔들림이 있다
- `delay()`로 기다리면 다른 작업이 멈추므로, `millis()`로 경과 시간만 확인하는 논블로킹 방식을 쓴다
- 디바운싱 시간(50ms)은 반응 속도와 안정성 사이의 트레이드오프다

## 4. 읽기 간격을 줄이자 물체 감지가 2번 카운트됨 (바운싱)

**문제**
- 05 실습에서 센서 읽기 간격(`SENSOR_INTERVAL`)을 100ms → 1ms로 줄이자, 적외선 센서(슬라이드 스위치로 대체)를 빠르게 두 번 클릭했을 때 감지는 1번인데 카운트가 **2번** 증가함

**원인**
- 스위치 접점이 바뀌는 순간 수 ms 동안 신호가 흔들린다 (바운싱)
- 1ms 간격으로 읽으면 흔들리는 동안 여러 번 읽게 되어, `HIGH → LOW` 변화를 2번 감지

```
실제 신호:  HIGH ─┐┌┐┌──────┐┌┐┌─ HIGH
                 └┘└┘      └┘└┘
                 ↑ 흔들림    ↑ 흔들림
```

**해결 및 비교**
| 읽기 간격 | 결과 |
|---|---|
| 1ms | 2번 카운트 ❌ |
| 100ms | 1번 카운트 ✅ |

- 100ms 간격에서는 흔들림이 끝난 뒤에 읽게 되어 정상 동작

**한계**
- 흔들리는 순간에 마침 읽으면 여전히 오류가 날 수 있다 (확률이 낮을 뿐)
- 100ms보다 짧게 지나가는 물체는 읽는 사이에 지나가 **아예 놓칠 수 있다**

| 읽기 간격 | 장점 | 단점 |
|---|---|---|
| 짧게 | 빠른 물체도 감지 | 바운싱에 약함 |
| 길게 | 바운싱에 강함 | 빠른 물체를 놓침 |

**개선 (06 Structure에서 해결)**
- 자주 읽으면서도 값이 일정 시간 유지될 때만 인정하는 **안정 시간 디바운싱 클래스**(`DebouncedInput`)를 만들어 버튼·적외선·PIR에 공통 적용
- 디바운싱이 흔들림을 처리하므로 입력 읽기 주기를 100ms → **5ms**로 줄여 반응 속도도 개선

**해결 확인 (읽기 주기를 1ms로 고정하고 디바운싱 값만 변경)**
| `INPUT_INTERVAL` | `IR_DEBOUNCE_MS` | 결과 |
|---|---|---|
| 1ms | 0 | 가끔 2번 카운트 ❌ |
| 1ms | 30 | 항상 1번 카운트 ✅ |

- 처음에는 5ms 주기에서 디바운싱을 0으로 바꿨는데 문제가 재현되지 않았다. 5ms 읽기 주기 자체가 짧은 흔들림을 건너뛰어 **두 효과가 섞였기 때문**이다. 읽기 주기를 1ms로 고정하고 디바운싱 값만 바꿔 원인을 분리했다.

**배운 점**
- 읽기 주기 자체가 노이즈 필터 역할을 하지만, 반응 속도와 트레이드오프 관계다
- 같은 문제(바운싱)도 해결 방법마다 한계가 다르므로, 요구사항(감지해야 할 물체 속도 등)에 맞춰 선택해야 한다
- 원인을 검증할 때는 변수를 하나만 바꾸고 나머지는 고정해야 결과를 확실히 해석할 수 있다

## 5. Wokwi 시뮬레이션에서 Wi-Fi가 연결되지 않음

**문제**
- 07 실습에서 시리얼이 `WiFi connecting...`에서 멈추고 더 진행되지 않음
- Wokwi Wi-Fi 메뉴의 데이터 표시: 보냄 ⬆3.8KB, 받음 ⬇**0B**

**원인 추적**
1. 보낸 데이터는 있고 받은 데이터가 0 → ESP32는 요청을 보내지만 응답을 전혀 받지 못함
2. 시뮬레이터 오류 메시지 확인: `WiFi Error: Connection to IoT Gateway wss://netwi.wokwi.com/ failed`
3. 시뮬레이션 속 Wi-Fi는 **내 브라우저 → Wokwi 게이트웨이 → 인터넷** 경로로 연결된다. 코드가 아니라 **브라우저가 게이트웨이에 접속하지 못한 것**이 원인

**해결**
- 시크릿 창에서 실행하자 정상 연결
- 일반 창과 시크릿 창의 차이(확장 프로그램, 사이트 캐시·쿠키)나 일시적인 게이트웨이 장애가 원인으로 추정. 방화벽은 컴퓨터 전체에 적용되므로 시크릿 창에서 된 이상 원인이 아님

**함께 확인한 점**
- Wi-Fi 연결이 안 되는 동안에도 OLED와 센서는 정상 동작했다. `WiFi.begin()`을 논블로킹으로 사용했기 때문

**배운 점**
- 오류 메시지와 데이터 흐름(보냄/받음)으로 문제 범위를 코드 → 개발 환경으로 좁힐 수 있다
- 조건을 하나만 바꿔(일반 창 → 시크릿 창) 원인 후보를 분리한다

## 6. MQTT 연결 실패 시 메인 루프가 3초씩 멈춤

**문제**
- 브로커 주소를 일부러 틀리게 바꾸자, 약 2초 동작 → 3초 멈춤이 반복됨
- 멈춘 동안 화면·버튼·센서가 모두 정지

**측정** (`mqtt.connect()` 전후 `millis()` 차이)
| 상황 | `MQTT_HOST` | 연결 시도 시간 |
|---|---|---|
| 정상 | `broker.hivemq.com` | 약 1,115ms |
| 없는 주소 | `no-such-broker.invalid` | 3,165~3,329ms |
| 응답 없는 주소 | `10.255.255.1` | 3,004~3,005ms |

**원인**
- `mqtt.connect()`는 **블로킹 함수**다. 연결에 성공하거나 포기할 때까지 `loop()` 전체가 멈춘다
- 없는 주소는 주소 찾기(DNS) 대기, 응답 없는 주소는 약 3초의 연결 대기 시간 초과로 실패
- 재연결 간격 5초를 **시도 시작 시점**부터 재서, 3초 멈춘 뒤 2초만 동작 → 브로커 장애 시 **시간의 약 60%를 멈춤**

**해결: 지수 백오프 + 시도 종료 시점부터 간격 측정**
```cpp
bool ok = tryConnectMqtt();
lastReconnect = millis();                 // 시도가 끝난 시점부터 측정
if (ok) reconnectDelay = RECONNECT_MIN;   // 성공하면 5초로 초기화
else    reconnectDelay = min(reconnectDelay * 2, RECONNECT_MAX);   // 실패할수록 2배, 최대 60초
```

| 재시도 간격 | 5초 | 10초 | 20초 | 40초 | 60초 |
|---|---|---|---|---|---|
| 멈춤 비율 | 38% | 23% | 13% | 7% | **약 5%** |

- 개선 후 `Next MQTT retry in 10 s, 20 s ...` 출력과 멈춤 빈도 감소를 확인
- 지수 백오프는 서버 장애 시 많은 기기가 동시에 재접속해 서버를 더 괴롭히는 것도 막아 준다

**한계와 향후 개선**
- 한 번 시도할 때 3초 멈추는 것 자체는 그대로다
- 근본적 해결: 네트워크 처리를 별도 FreeRTOS 태스크(다른 코어)로 분리해 메인 루프가 멈추지 않게 하기

**배운 점**
- 체감("멈칫한다")을 측정값(ms)으로 바꿔야 원인을 정확히 설명할 수 있다
- 라이브러리 함수가 블로킹인지 확인하고, 실패 상황을 일부러 만들어 시스템이 어떻게 버티는지 테스트해야 한다
